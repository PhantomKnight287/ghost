Prerequisite: Storage. The merging and pull refs lessons are where storage rules matter most outside a push.

<Cards>
  <Card title="Issues" href="/issues-and-pull-requests/issues">Rows, not branches. Six tables, numbering without locks, and a timeline that only grows.</Card>
  <Card title="References and closing keywords" href="/issues-and-pull-requests/references">#123, owner/repo#5, @user, @org/team, and fixes #12 in a commit message.</Card>
  <Card title="Pull requests across two logs" href="/issues-and-pull-requests/pull-requests">A pull request is a row naming two (repository, branch) pairs. Reading one lends objects between caches instead of copying them.</Card>
  <Card title="Merging" href="/issues-and-pull-requests/merging">Merge, squash and rebase, all built in the base cache and landed through commitPush, and the one shortcut that would corrupt a log.</Card>
  <Card title="refs/pull/N/head and /merge" href="/issues-and-pull-requests/pull-refs">GitHub-compatible pull request refs, kept in the base log by a background sync.</Card>
  <Card title="Reviews and suggestions" href="/issues-and-pull-requests/reviews">Reviews pinned to the head they read, threads hanging off line comments, and suggestions applied as commits.</Card>
  <Card title="Commits on the timeline" href="/issues-and-pull-requests/timeline">Why a pull request's commits are rows written as each push lands, not read from git.</Card>
