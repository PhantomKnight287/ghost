---
title: Building an OAuth app
description: Register an app, send people to Ghost to approve it, and exchange the code for a token that calls the API
---

An OAuth app lets your tool act on someone's Ghost account without asking for their password. The person approves the app once, choosing what it may do, and your app receives a token it can call the API with. Ghost speaks GitHub's OAuth: a library or tool written for GitHub OAuth apps works against Ghost once you point it at your Ghost host.

The flow has three parts:

1. You register the app once and get a **client ID** and a **client secret**.
2. Your app sends each person to Ghost, where they approve it. Ghost sends them back to your app with a one-time **code**.
3. Your app exchanges the code, with its secret, for an **access token**.

In the examples below, `api.<domain>` is your Ghost API host and `<web>` is the Ghost web app.

## Register the app

Open **Settings → OAuth apps** and choose **New OAuth app**.

![The OAuth apps page in settings, before any app is registered](/images/oauth-apps/oauth-apps-empty.png)

Fill in the form:

- **Application name**: what people see when your app asks for access.
- **Description**: optional. One or two sentences on what the app does, shown on the approval page.
- **Homepage URL**: your app's website.
- **Callback URLs**: where Ghost sends people after they approve the app. Add your production callback and, while you develop, a `http://localhost` one. See [Callback URLs](#callback-urls) for the rules.
- **Enable device flow**: only for command-line tools and devices that cannot receive a callback. See [The device flow](#the-device-flow).

![The form for registering a new OAuth app, filled in for an app named Release bot with two callback URLs](/images/oauth-apps/oauth-app-new.png)

Choose **Register application**. Ghost shows the client ID and the client secret.

![The registered app's client ID and client secret, with copy buttons](/images/oauth-apps/oauth-app-credentials.png)

<Callout type="warn">
Copy the client secret now. Ghost keeps only a hash of it and cannot show it again. Keep it on your server, never in a browser, a mobile app or a public repository. If you lose it, generate a new one.
</Callout>

The app's page then holds everything you can change later: the credentials, a logo, the settings, and deleting the app.

![The settings page of the Release bot app: credentials, logo, settings and delete](/images/oauth-apps/oauth-app-settings.png)

### Callback URLs

- Use `https://`, or `http://` on `localhost`, `127.0.0.1` or `[::1]` while you develop. Plain `http://` on any other host is refused.
- An app can have up to 10 callback URLs.
- When your app names a `redirect_uri`, it must have the same scheme, host and port as one of the callback URLs, and its path must equal that callback's path or sit under it. With a callback of `https://bot.example/oauth/callback`:

| `redirect_uri` | Accepted |
|---|---|
| `https://bot.example/oauth/callback` | Yes |
| `https://bot.example/oauth/callback/github` | Yes |
| `https://bot.example/oauth/callback?next=%2Fhome` | Yes |
| `https://bot.example/elsewhere` | No: path outside the callback |
| `https://bot.example:8443/oauth/callback` | No: another port |
| `https://evil.example/oauth/callback` | No: another host |

- When your app names no `redirect_uri`, Ghost uses the first callback URL.

## Send people to Ghost to approve the app

Redirect the person's browser to:

```txt
https://api.<domain>/login/oauth/authorize
```

with these query parameters:

| Parameter | Required | Description |
|---|---|---|
| `client_id` | Yes | Your app's client ID. |
| `redirect_uri` | No | Where to send the person back. Must match one of the callback URLs as described above. Defaults to the first one. |
| `scope` | No | Space-separated [scopes](#scopes). Without one, the app may read public information only. |
| `state` | Recommended | A random value your app makes up for this request. Ghost sends it back unchanged; check it to stop cross-site request forgery. |
| `code_challenge` | No | For [PKCE](#pkce). |
| `code_challenge_method` | No | `S256`, with `code_challenge`. |

For example:

```txt
https://api.<domain>/login/oauth/authorize?client_id=DEyiWXBFvHvUTGkCIQzDrbNEuetuxVOr&redirect_uri=https%3A%2F%2Fbot.example%2Foauth%2Fcallback&scope=repo%20read%3Aorg&state=af0ifjsldkj
```

If the person is not signed in, Ghost asks them to sign in first. Then it shows what your app is asking for:

![Ghost asking the signed-in person to authorize Release bot with the repo and read:org scopes](/images/oauth-apps/oauth-consent.png)

When the person chooses **Authorize**, Ghost redirects to your callback with a `code` and your `state`:

```txt
https://bot.example/oauth/callback?code=k8DfjBZl4QVfliGLImbhbIKc7qUaNvZE&state=af0ifjsldkj&iss=https%3A%2F%2Fapi.<domain>%2Fapi%2Fauth
```

The code is valid for 10 minutes and can be exchanged once. Ghost also adds `iss`, which your app can ignore.

When the person chooses **Cancel**, Ghost redirects with `error=access_denied` and your `state` instead of a code:

```txt
https://bot.example/oauth/callback?error=access_denied&state=af0ifjsldkj
```

A person who already approved the same scopes, or more, is not asked again: Ghost redirects straight back with a new code.

<Callout>
An unknown `client_id`, or a `redirect_uri` that matches none of the callback URLs, shows an error page on Ghost and never redirects. Check the app's callback URLs if people land there.
</Callout>

## Exchange the code for a token

Your server sends the code and the client secret to:

```txt
POST https://api.<domain>/login/oauth/access_token
```

| Parameter | Required | Description |
|---|---|---|
| `client_id` | Yes | Your app's client ID. |
| `client_secret` | Yes | Your app's client secret. |
| `code` | Yes | The code from the callback. |
| `redirect_uri` | If you sent one | The same `redirect_uri` the authorize request used. |
| `code_verifier` | With PKCE | The verifier behind the `code_challenge`. |

GitHub's clients send no `grant_type` here, and Ghost needs none. Send the body form-encoded or as JSON.

<Tabs items={["curl", "JavaScript"]}>
<Tab value="curl">

```bash
curl -X POST https://api.<domain>/login/oauth/access_token \
  -H "Accept: application/json" \
  -d client_id=DEyiWXBFvHvUTGkCIQzDrbNEuetuxVOr \
  -d client_secret="$GHOST_CLIENT_SECRET" \
  -d code=k8DfjBZl4QVfliGLImbhbIKc7qUaNvZE \
  -d redirect_uri=https://bot.example/oauth/callback
```

</Tab>
<Tab value="JavaScript">

```js
const response = await fetch("https://api.<domain>/login/oauth/access_token", {
  method: "POST",
  headers: { "Content-Type": "application/json", Accept: "application/json" },
  body: JSON.stringify({
    client_id: process.env.GHOST_CLIENT_ID,
    client_secret: process.env.GHOST_CLIENT_SECRET,
    code,
    redirect_uri: "https://bot.example/oauth/callback",
  }),
});
const { access_token, error } = await response.json();
```

</Tab>
</Tabs>

With `Accept: application/json`, Ghost answers JSON:

```json
{
  "access_token": "ghost_pat_KOYduxMKlnMGQKszNbnWWRxpLOivafxX…",
  "token_type": "bearer",
  "scope": "repo,read:org"
}
```

Without it, Ghost answers form-encoded, as GitHub does:

```txt
access_token=ghost_pat_UxkahUQBptnqPZulFOGmJEniHcUnmCxK…&token_type=bearer&scope=repo%2Cread%3Aorg
```

`scope` lists, comma-separated, the scopes the person approved that Ghost knows. Check it: it can be narrower than what your app asked for.

### Errors

Failures also answer HTTP 200, with an `error` field instead of a token:

| `error` | Cause |
|---|---|
| `incorrect_client_credentials` | Unknown `client_id`, or a wrong or replaced `client_secret`. |
| `bad_verification_code` | The code is wrong, expired, already used, belongs to another app, was issued for another `redirect_uri`, or the `code_verifier` does not match. |
| `redirect_uri_mismatch` | The `redirect_uri` matches none of the app's callback URLs. |

A failed exchange uses the code up, so start again from the authorize step.

## Call the API

The token is an API key starting with `ghost_pat_`. Send it in the `Authorization` header, as `Bearer` or `token`:

```bash
curl https://api.<domain>/api/v3/user \
  -H "Authorization: Bearer $GHOST_TOKEN" \
  -H "Accept: application/vnd.github+json"
```

```http
HTTP/1.1 200 OK
X-OAuth-Scopes: repo, read:org

{
  "login": "demoalice",
  "type": "User",
  "html_url": "https://<web>/demoalice",
  …
}
```

It works with Ghost's GitHub-compatible REST API under `/api/v3` and GraphQL API at `/api/graphql`; see [GitHub CLI](/github-compatibility) for what they serve. It also works as the password for `git` over HTTPS. Every response carries `X-OAuth-Scopes`, the scopes the token holds. A REST request that needs a scope the token lacks answers 403 with `X-Accepted-OAuth-Scopes` naming the scopes that would do; GraphQL answers a `FORBIDDEN` error.

The token does not expire. It stops working when the person revokes the app, or when you delete the app. Ghost's own API under `/api`, which the web app uses, refuses these tokens with 401.

## Scopes

Ghost uses GitHub's scope names. What each one guards today:

| Scope | What Ghost checks |
|---|---|
| (none) | Public information only. Private repositories answer as if they did not exist. |
| `repo` | Reading private repositories, and writing to any repository: issues, comments, labels, creating repositories, and `git push`. Includes `public_repo`. |
| `public_repo` | Writing to public repositories, including `git push`. |
| `read:public_key` | Listing the person's SSH keys. |
| `write:public_key` | Adding SSH keys. Includes `read:public_key`. |
| `admin:public_key` | Includes `write:public_key` and `read:public_key`. |

`read:org`, `write:org`, `admin:org`, `user`, `read:user`, `user:email`, `delete_repo` and `gist` are accepted and recorded on the token, so tools written for GitHub keep working, but nothing in Ghost checks them yet. Scopes Ghost does not know at all, such as `workflow`, are dropped rather than refused.

Ask for the fewest scopes your app needs; people are likelier to approve a short list.

## PKCE

PKCE proves that the server exchanging a code is the one that started the request. It is optional, and worth using. Make a random verifier for each request, keep it, and send its SHA-256 as the challenge:

```bash
verifier=$(openssl rand -base64 48 | tr -d '=+/' | cut -c1-64)
challenge=$(printf '%s' "$verifier" | openssl dgst -sha256 -binary | openssl base64 | tr '+/' '-_' | tr -d '=')
```

Add `code_challenge=$challenge&code_challenge_method=S256` to the authorize URL, and `code_verifier=$verifier` to the token request. A code requested with a challenge cannot be exchanged without the matching verifier.

## The device flow

Command-line tools and devices that cannot receive a callback use the device flow, as `gh auth login --web` does. Turn on **Enable device flow** in the app's settings first; Ghost refuses device codes for apps without it.

1. Ask for a device code:

   ```bash
   curl -X POST https://api.<domain>/login/device/code \
     -H "Accept: application/json" \
     -d client_id=DEyiWXBFvHvUTGkCIQzDrbNEuetuxVOr \
     -d scope=repo
   ```

   ```json
   {
     "device_code": "XUNcGWbIlQkErNKuRnc2jOwijqRBr203qvVoNZCx",
     "user_code": "DVZUJBJ9",
     "verification_uri": "https://<web>/device",
     "expires_in": 1800,
     "interval": 5
   }
   ```

2. Show the person the `user_code` and the `verification_uri`. They open it, enter the code, and approve:

   ![Ghost asking the person to approve a device request from Release bot](/images/oauth-apps/device-approval.png)

3. Meanwhile, poll for the token every `interval` seconds:

   ```bash
   curl -X POST https://api.<domain>/login/oauth/access_token \
     -H "Accept: application/json" \
     -d client_id=DEyiWXBFvHvUTGkCIQzDrbNEuetuxVOr \
     -d device_code=XUNcGWbIlQkErNKuRnc2jOwijqRBr203qvVoNZCx \
     -d grant_type=urn:ietf:params:oauth:grant-type:device_code
   ```

   Until the person decides, Ghost answers HTTP 200 with `{"error": "authorization_pending"}`. Keep polling. On `slow_down`, wait longer between polls. `expired_token` means the code ran out; `access_denied` means the person said no. Once they approve, the answer is a token, in the same shape as the code exchange.

The device flow needs no client secret, so a tool can ship its client ID in its code.

## Manage and revoke access

On the app's page you can:

- **Generate a new secret.** The old one stops working at once, so update your app's configuration straight away.
- **Upload a logo.** People see it next to your app's name when it asks for access.
- **Edit** the name, description, homepage, callback URLs and device flow.
- **Delete the app.** Every token it was given, for every person, stops working.

People see every app holding a token for their account under **Settings → Authorized apps**, with the scopes it holds. **Revoke** ends that app's access to their account, and the app has to ask again next time.
