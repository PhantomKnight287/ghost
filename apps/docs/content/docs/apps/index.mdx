---
title: Building a Ghost App
description: Register a bot that acts as itself, give it a private key, and authenticate as it with a JWT
---

A Ghost App is a bot that acts as itself: a CI service posting commit statuses, a reviewer commenting on pull requests, a scanner reading pushes. It works the way a GitHub App does, so an app built with Octokit or Probot mostly runs against Ghost once you point it at your Ghost API.

An app differs from an [OAuth app](/oauth-apps) in three ways:

- **It has its own identity.** Everything it does shows as its bot, `<slug>[bot]`, not as a person.
- **It has narrow access.** It asks for fine-grained permissions and gets them only on the repositories it is installed on.
- **It proves who it is.** Only the holder of one of its private keys can authenticate as the app.

In the examples below, `api.<domain>` is your Ghost API host and `<web>` is the Ghost web app.

## Register the app

Open **Settings → Ghost Apps** and choose **New Ghost App**. To register it for an organization, open `<web>/<org>/settings/apps` instead: every admin and owner of the organization can manage it there.

Fill in the form:

- **App name**: up to 34 characters. Ghost makes the app's **slug** from it, and its bot is `<slug>[bot]`. The slug never changes, even when you rename the app.
- **Description** and **Homepage URL**: shown on the app's public page.
- **Setup URL**: optional. Where Ghost sends someone after they install the app.
- **Webhook URL** and **secret**: where Ghost will deliver the events the app subscribes to, signed with the secret. The secret is never shown again once saved.
- **Permissions**: what the app may do on the repositories it is installed on. Ghost uses GitHub's permission names.
- **Events**: what Ghost tells the app about. Each event needs read on the permission it belongs to, so the form offers only the events your permissions cover.

| Permission | `read` | `write` |
|---|---|---|
| `metadata` | always granted: the repository, its branches and collaborators | — |
| `contents` | files, commits, diffs, clone and fetch | push, refs, releases |
| `pull_requests` | pull requests, reviews, review comments | open, edit, review, comment, merge |
| `issues` | issues, comments, labels | create, edit, comment, label |
| `statuses` | commit statuses | post commit statuses |
| `members` | organization members and teams | — |

Every app has a public page at `<web>/apps/<slug>` and an install link. Anyone with the link can see the page; there is no directory of apps.

## Generate a private key

On the app's settings page, choose **Generate a private key**. Your browser downloads a `.pem` file. Ghost keeps only the public half, so this is the only copy: store it as a secret on the server the app runs on.

An app can hold up to 20 keys. To rotate one, generate a new key, deploy it, then delete the old one. A deleted key stops working at once.

## Authenticate as the app

The app signs a JSON Web Token with its private key and sends it as `Authorization: Bearer <jwt>`. The token must be:

- signed with **RS256** by one of the app's current keys;
- issued by the app: `iss` is the **App ID** shown on the settings page;
- issued no more than 60 seconds in the future (`iat`), to allow for clock drift;
- short-lived: `exp` no more than 10 minutes after `iat`, and not yet passed.

Octokit does all of this for you:

```ts
import { App } from "@octokit/app";

const app = new App({ appId: 12, privateKey: process.env.PRIVATE_KEY });
const { data } = await app.octokit.request("GET /app", {
  baseUrl: "https://api.<domain>/api/v3",
});
console.log(data.slug, data.permissions);
```

`GET /api/v3/app` answers with the app, in GitHub's shape. A JWT can call only the app's own endpoints; anywhere else Ghost answers `403 Resource not accessible by integration`. A token Ghost cannot verify gets `401 A JSON web token could not be decoded`.

## Install the app

Open the app's install link, `<web>/apps/<slug>/installations/new`. Pick the account to install it on: yours, or an organization you administer. Then pick **All repositories**, which includes ones created later, or **Only select repositories**. The page lists what the app will be able to do.

The installation accepts the app's permissions and events as they are when you install it. Until Ghost can ask you to review new permissions, an app with installations can lower its permissions but not raise them.

After you install, Ghost sends you to the app's setup URL with `?installation_id=<id>&setup_action=install`, or to your installed apps when there is none.

Manage installations under **Settings → Installed apps**, or `<web>/<org>/settings/installations` for an organization. From there you can change the repositories, suspend the app, or uninstall it. Suspending or uninstalling stops every token of the installation at once.

## Act as the installation

With its JWT, the app finds its installations and mints an installation token for one of them. The token starts with `ghs_` and lasts an hour:

```ts
const octokit = await app.getInstallationOctokit(installationId);
await octokit.request("POST /repos/{owner}/{repo}/issues/{issue_number}/comments", {
  owner, repo, issue_number: 1, body: "Checked by the bot",
});
```

For this to reach Ghost, pass `Octokit: Octokit.defaults({ baseUrl: "https://api.<domain>/api/v3" })` from `@octokit/core` to `new App(...)`.

These endpoints take the app's JWT, at GitHub's paths:

| Endpoint | What it does |
|---|---|
| `GET /app/installations`, `GET /app/installations/{id}` | the app's installations |
| `DELETE /app/installations/{id}` | uninstall from an account |
| `POST /app/installations/{id}/access_tokens` | mint a token; `permissions`, `repositories` and `repository_ids` narrow it, never widen it |
| `GET /repos/{owner}/{repo}/installation`, `GET /users/{username}/installation`, `GET /orgs/{org}/installation` | the installation covering a repository or account |

The token works on the GitHub-compatible REST API (`Authorization: token ghs_...`) and as the password for git over HTTPS (`https://x-access-token:ghs_...@<host>/<owner>/<repo>.git`). `GET /installation/repositories` lists what it reaches. Everything it writes shows as `<slug>[bot]`, and commit statuses it posts record the installation.

### What a token may call

A token reaches only the repositories of its installation, and only as far as the installation's permissions allow:

- each endpoint needs the permission it belongs to, at `read` for `GET` and `write` for anything else; git needs `contents`, at `write` to push;
- on a public repository outside the installation, or beyond its permissions, the token reads what anyone can read, and writes nothing;
- a private repository outside the installation answers `404`;
- anything else answers `403 Resource not accessible by integration`.

Some endpoints are never open to a token: the `/user` endpoints, repository settings and deletion, creating repositories, ruleset changes and rule suites. GraphQL and Ghost's own API refuse installation tokens too.

## Rulesets and apps

A required status check can name an app with `integration_id`, its App ID. Only a status that app posted with an installation token meets the check; the same context posted by anyone else does not count. In the ruleset form, pick the app as the check's source.

A ruleset can also let an app bypass it: add the app to the bypass list, or send `{ "actor_type": "Integration", "actor_id": <App ID> }` over the API. An app's bot never bypasses through a repository role.

An approving review from a bot counts toward required approvals. It counts as a code owner's review only when CODEOWNERS names the bot, as `@<slug>[bot]`.

## Deleting an app

Deleting an app stops its keys at once and removes its installations, so every token stops too. Its bot stays, so issues, comments and statuses it made keep showing who made them, and its App ID, slug and bot name are never given to another app. A ruleset check pinned to a deleted app can no longer pass; the ruleset form flags it so you can change it.
